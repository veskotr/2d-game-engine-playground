Follow Player through the engine

Use the saved First Room project and press D in Play to connect the code below to three visible results. Player moves, Wall stops the body, and the checkpoint changes the HUD.

Load the saved scene

On a folder-project launch, Runtime::startProject registers the project's scene documents and loads the startup scene selected by its descriptor. Project asset resolution maps UUID references to files such as the Player texture and movement script. Follow ProjectRuntime and Runtime.

SceneLoader expands prefabs, creates entities, reads their component definitions through registered codecs, and resolves hierarchy links. In First Room, Player's saved definition becomes a runtime entity with a Transform, SpriteRenderer, Script, RigidBody, and BoxCollider. The camera is its own entity. See SceneLoader and scene identity and formats.

Read Player in ECS

Player's entity ID identifies it within the active registry. The registry holds its component data, while Scene tracks parent and child relationships. Keep authored scene keys for document references and query live IDs against the current registry. See the Scene module and ECS guide.

Use Registry::view to query combinations of components the system needs, such as transforms and sprites. Use the registry's component access helpers for a specific live entity and reacquire component pointers after structural changes. See Registry and RenderSystem.

Resolve Player's world pose

The authored Transform stores a local pose. Player is a root, so its parent pose is the identity. For a child, the system composes its local pose with the parent's world pose. TransformSystem visits parents before children, refreshes cached world transforms when a local or parent pose is dirty, and clears local dirty flags. Use Transform setters when changing a local pose so the next update picks it up. A parent without its own local Transform passes the inherited pose through. See TransformSystem and the engine constraints.

Trace one running frame

The two runtime methods to follow are advanceSimulation and advanceAndRender. The standalone loop processes pending scene switches and polls window events before advancing and presents after rendering. Editor Play advances the same simulation and can draw a separate view of the resulting state. See Runtime and the runtime guide.

  1. Sample input actions and flush queued scene and global events. A checkpoint contact queued during an earlier physics step can reach Player's Lua subscription here.
  2. Update chunk activity, animation, and audio requests. Run Lua behaviours, then update state machines. Player's movement behaviour reads MoveLeft and MoveRight, requests a world-space body velocity through Engine.Physics.setVelocity, and publishes its checkpoint state with Engine.setUIBinding. See the Scripting module and generated Lua API.
  3. Synchronize authored poses to physics, step Box2D using its fixed-step accumulator, and write simulated poses back into local transforms. Wall blocks Player. Checkpoint is a sensor and queues overlap events for a subsequent queue flush. See PhysicsSystem, the Physics module, and the Events module.
  4. Resolve final world transforms and update the gameplay camera. Putting this after physics lets rendering use Player's resolved position from the current frame.
  5. Submit scene draw commands through RenderSystem and process the XML HUD through UISystem. The HUD reads the roomStatus binding. Renderer owns command sorting, batching, and drawing. See the Renderer module and the UI module.

Find the owning module

Systems coordinates the frame through sle::engine, the CMake alias for sle_engine. Keep components data-centric, query the scene in systems, and expose Lua functionality through bindings and the runtime bridge. The modules form a dependency graph. Check direct dependencies in the target definitions before adding a cross-module call. See the architecture guide, Systems module, and Systems CMake target.

Run a smaller example

  • Sandbox builds as example_sandbox for exploring engine setup and rendering.
  • Phase 1 EventBus builds as example_phase1_eventbus for C++ event dispatch.
  • Phase 2 Lua Events builds as example_phase2_lua_events for Lua event handling.
  • Phase 3 Advanced Events builds as example_phase3_advanced_events for handler priority, cancellation, and subscription filters.

Build examples in the Debug tree and run from the repository root after the quickstart setup.

Validate changes

For boot and shutdown checks, build the Debug tree and run the CTest smoke label.

cmake --build build/debug --config Debug --parallel
ctest --test-dir build/debug -C Debug -L smoke --output-on-failure

For a subsystem change, rebuild the affected target and run just its test. The reference lists checks for scene loading, transforms and physics, events, Lua, and UI. See the testing guide for labels and windowed checks.
