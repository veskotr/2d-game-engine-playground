# Runnable project distribution

## Approved scope and implementation choices

The user approved the proposed runnable delivery folder: copy saved project assets
with UUIDs, bundle the standalone engine/resources, exclude local editor state and
validate after relocation from an unrelated cwd. Continue inline on the existing
`feat/project-foundation` checkout; preserve every inherited uncommitted file.

First format: a Windows x64 Release folder. A new CMake `sle_runtime_bundle` target
stages `engine_app.exe`, release CRT/non-system dependent DLLs, engine resources,
third-party notices and a versioned `sle-runtime.json` manifest. Debug bundles are
rejected. No compiler invocation or dependency download is hidden behind export.

Export layout: runtime files at the delivery root; `game/game.sleproject` plus the
configured relative asset tree beneath `game/`. The standalone executable chooses
that descriptor beside itself on a no-config launch; explicit `--config`/`--project`
keep their current behavior. All asset files and sidecars are copied, including
unknown formats and Lua module directories: dependency pruning cannot infer dynamic
paths. Plain source folders remain authoritative; no encrypted archive, streaming,
multiple packs, installer or cross-platform runtime is introduced.

Copy into a unique sibling staging folder, validate the staged project through the
existing native resolver, check source/bundle inventories for changes, remove only
staged `.sle` caches, then publish with a no-overwrite directory move. Never modify
source payloads, assign source UUIDs, replace an existing destination or export
inside the source/bundle. File changes, invalid IDs, missing references, links,
missing runtime files and native validation failure must leave the final destination
absent and preserve sources. Source drafts are excluded explicitly; export does not
reset workspaces or playback. Runtime/project format compatibility is checked by
native validation; exported manifest records SHA-256 inventory, not asset identity.

UI: File → Export Game… chooses a prepared runtime bundle, then a new output folder;
background work reports success/failure and preserves current authoring documents.
Export consumes saved files and states that clearly before choosing output.
